# Contributing

Thanks for looking. This is a small project, so the bar for a change is mostly:
does it make the thing simpler to run, or fix something that's wrong?

## Get set up

You'll need Node 24 or newer and a Unix-like system.

```bash
git clone https://github.com/murerkinn/bookshelf.git
cd bookshelf
npm install
```

Run these before you push:

```bash
npm run lint          # Biome — formatting and lint in one pass
npm run format        # write the formatting fixes
npm run check-types   # typecheck every workspace
npm test              # the test suite
```

Two things that will look wrong and aren't:

- **`public/pdfjs/` appears in the app.** The `assets` task copies pdf.js's
  worker, CMaps, fonts and wasm out of `pdfjs-dist`, because pdf.js fetches
  those by URL and no bundler sees the request. It's gitignored, everything that
  serves the app depends on it, and you never run it by hand.
- **`check-types` is slower than you'd expect.** It builds first, because the
  app's route types are generated by `next build`.

CI runs lint, build and typecheck on Node 24, bundles the Worker separately — a
change can pass `next build` and still fail for workerd — and runs the tests.

## Where things live

```
apps/bookshelf       the app — a Next.js Worker, or a Node server
packages/core        the library format, the readers, the provider contract
packages/provider-r2 Cloudflare R2
packages/provider-fs a directory on disk
packages/sync        the CLI that builds a library and publishes it
packages/fixtures    generated books, for tests and the demo shelf
```

[Architecture](docs/architecture.md) has the detail, and the rules you need to
respect when adding to the service layer.

## Tests

`npm test` runs everything through Turborepo, so a change to one package re-runs
only what depends on it. `npm test -w @bookshelf/core` runs a single package's.

Put tests beside the code they exercise, as `test/*.test.ts`. Node runs them
from source, and they're typechecked by the package's own `check-types`.

**Don't add a book to the repository to test against.** `@bookshelf/fixtures`
generates real EPUBs and real PDFs — real ZIP, real PNG cover, real Dublin Core
— one per combination of the ways a format can record the same thing. Nothing
reaches the network or needs `cwebp` or `pdftoppm` installed, and the output is
deterministic so it can be compared.

For the app, use the fakes in `apps/bookshelf/test/lib/storage.ts`: a library in
memory that counts what was asked of it, and can be told to be unwritable, to
fail, or to fail only some operations. Use that last one when you're changing
anything that reads before it writes — a read that fails while writes still work
is how a rewritten file loses everything it couldn't read first.

Pages aren't reachable from tests; they need `next/headers` and a Cloudflare
context. Routes and services are. If your change touches a page, run it and say
so on the pull request.

Prefer pinning a promise over an implementation. The tests worth having are the
ones a future change can quietly break — that an entry costs one ranged read,
that `--force` can't take everyone's bookmarks with it, that a range a provider
declined comes back as a whole object.

Two workarounds you'll run into: `apps/bookshelf/test/lib/alias.mjs` registers a
resolver because Node doesn't know the app's `@/` path alias, and
`tsconfig.test.json` exists because the app excludes `test` from
`tsconfig.json` so `next build` doesn't compile tests into the bundle.

## Adding a storage provider

You don't have to contribute one here — a package published by anyone can be
installed and named in `bookshelf.config.json`. If you do want it shipped in
this repository, copy `packages/provider-fs` and read
`packages/core/src/provider.ts` first.

Five things to get right:

**Name your entry points for the runtime they need, not the face they
implement.** `/worker` for workerd, `/node` for Node. Never let a Node-only
import be reachable from a `/worker` entry point — CI bundles the Worker partly
to catch that.

**Declare only the capabilities you have.** `create`, `list` and `removeAll` are
optional. Leave one undefined rather than half-implementing it: the sync tool
asks with `capabilitiesOf()` and degrades honestly, and `--force` tells the user
which guarantee it actually gave them.

**Keep `.bookshelf/` out of enumeration.** It holds profiles and reading
positions. `list` reports what the sync tool may remove, so if you report state
keys, `--force` will delete everyone's bookmarks. Use `isStateKey()` from
`@bookshelf/core`.

**Serve a range or decline it, but say which.** `read` takes an optional
`range`. Honour it and set `range` on what you return, naming the bytes the body
holds; ignore it and return the whole object with nothing set. Declining costs a
complete response, which is safe. Mislabelling a partial one as complete is not.

If you do implement ranges, clamp with `clampRange` — the size the route
measured and the object being read are two separate reads, so a range can be
past the end by the time it's served. Return no body when it returns null, and
the route answers `416`. And leave `size` alone: it stays the size of the whole
object even on a partial read, because that's the number `Content-Range` has to
name.

**Treat keys as untrusted.** They arrive from URLs. A key that escapes the
library must fail rather than be tidied up. `resolveKey` in
`packages/provider-fs/src/node.ts` is the reference.

## Commit messages

The seven rules from <https://chris.beams.io/git-commit>:

1. Separate subject from body with a blank line.
2. Limit the subject to about 50 characters.
3. Capitalise the subject.
4. No full stop at the end of the subject.
5. Imperative mood — the subject completes "If applied, this commit will ___".
   `Add reading dispatcher`, not `Added` or `Adds` or `Fixed`.
6. Wrap the body at 72 characters.
7. The body explains **what and why**, not how. Add one only when the change
   needs context; skip it for trivial changes.

Please don't add tool attribution trailers — no `Co-Authored-By` for an
assistant, no "generated with" lines, no emoji signatures. Using an assistant to
write the code is fine; the commit log is for explaining the change.

## Pull requests

Small and focused beats large and complete. If a change does two things, open
two pull requests.

Say what you verified and how. `npm test` passing is the baseline; "ran the
filesystem quickstart, opened a book, switched profiles" is what says the change
works, and pages are still only reachable that way.

`main` takes changes through pull requests only, and every CI job has to pass.
Merges are squashed, so use as many commits as you like on the branch and write
the final message on the pull request.

## License

This project is MIT, and contributions come in under the same terms: opening a
pull request is offering the change under [the MIT license](LICENSE). There's no
contributor agreement to sign and no copyright to assign — you keep yours.

Two things that asks of you.

**Submit only what you have the right to submit.** Code from somewhere else is
welcome where its license allows it, but say where it came from in the pull
request and keep whatever notice it arrived with.

**A new dependency has to be permissive, and has to be recorded.** MIT,
Apache-2.0, BSD and ISC are fine. Anything copyleft that would reach the Worker
bundle or the Docker image is not, because it would decide the license of the
whole thing. If it ships in either artifact, add it to
[THIRD-PARTY-NOTICES.md](THIRD-PARTY-NOTICES.md) in the same pull request.

**Please don't attach a book to an issue or a pull request.** It's almost
certainly copyrighted, and nothing here needs one — the metadata block from a
book's `.opf` is enough to reproduce anything, and the issue template asks for
exactly that.

## Reporting a security issue

Don't open a public issue for anything exploitable. See
[SECURITY.md](SECURITY.md), which covers where to send it and what doesn't count
— the missing authentication, chiefly.

# Contributing

Thanks for looking. This is a small project with a small surface, so the bar
for a change is mostly: does it make the thing simpler to run, or fix something
that is wrong?

## Getting set up

See [Getting started](README.md#getting-started) for prerequisites and the two
ways to run it. In short: Node 24 or newer, a Unix-like system, `npm install`.

Everything runs from the repository root, and Turborepo builds whatever a task
depends on first:

```bash
npm run lint          # Biome — formatting and lint in one pass
npm run format        # write the formatting fixes
npm run build         # every workspace
npm run check-types   # every workspace (builds first — see below)
npm run preview       # build and run the Worker locally
```

`check-types` builds before it typechecks, because the app's route types are
generated by `next build`. That is why it is slower than you might expect.

CI runs lint, build and typecheck on Node 24, and separately bundles the
Worker — a change can pass `next build` and still fail to bundle for workerd.

## There are no tests yet

That is the honest state of it. Until there are, verify by running the thing:
the filesystem quickstart in the README is the fastest way, and it exercises
publishing, the shelf, the reader and reading positions in about a minute.

`test/` holds the pieces to build on: `test/lib/epub.mjs` generates valid
EPUBs — real ZIP, real PNG cover, real Dublin Core metadata — with no network
and byte-for-byte determinism, and `test/fixtures.mjs` builds a whole shelf out
of them. `npm run demo` is that same code.

So the two most valuable tests are now both unblocked: a **provider conformance
suite**, and an end-to-end run of the quickstart against a generated library.
Both would be very welcome.

## What lives where

```
apps/bookshelf       the app — a Next.js Worker, or a Node server
packages/core        the library format, the ZIP reader, the provider contract
packages/provider-r2 Cloudflare R2
packages/provider-fs a directory on disk
packages/sync        the CLI that builds a library and publishes it
```

The app talks to interfaces and never to a specific provider. If you find
yourself importing `@bookshelf/provider-*` anywhere but
`apps/bookshelf/src/services/container.ts`, something has gone sideways.

## Adding a storage provider

Providers are the extension point, and they do not have to live here — a
package published by anyone can be installed and named in
`bookshelf.config.json`. If you want one shipped in this repository, copy
`packages/provider-fs` and read `packages/core/src/provider.ts` first.

Four things a provider has to get right:

**Name entry points for the runtime they need, not the face they implement.**
`/worker` for workerd, `/node` for Node. R2 has both because the app reads it
from a Worker binding and the CLI writes it through wrangler; the filesystem
has only `/node`, because both of its halves need a filesystem. Node-only
imports must never be reachable from a `/worker` entry point — CI bundles the
Worker partly to catch that.

**Declare only capabilities you have.** `create`, `list` and `removeAll` are
optional because storage APIs genuinely differ. Leave them undefined rather
than implementing something that half works: the sync tool asks with
`capabilitiesOf()` and degrades honestly, and `--force` tells the user which
guarantee it actually gave them.

**Keep `.bookshelf/` out of enumeration.** It holds profiles and reading
positions — the only things in a library the app wrote rather than the sync
tool. `list` reports what the sync tool may remove, so anything that reports
state keys will have `--force` delete everyone's bookmarks. `isStateKey()` in
`@bookshelf/core` is there for this.

**Treat keys as untrusted.** They arrive from URLs. Resolving one that escapes
the library must fail, not be tidied up; `resolveKey` in
`packages/provider-fs/src/node.ts` is the reference.

## Commit messages

The seven rules from <https://chris.beams.io/git-commit>:

1. Separate subject from body with a blank line.
2. Limit the subject to about 50 characters.
3. Capitalise the subject.
4. No full stop at the end of the subject.
5. Imperative mood — the subject completes "If applied, this commit will ___".
   `Add reading dispatcher`, not `Added` or `Adds` or `Fixed`.
6. Wrap the body at 72 characters.
7. The body explains **what and why**, not how; the diff shows how. Add one
   only when the change needs context — motivation, a side effect, a trade-off
   — and skip it for trivial changes.

Please don't add tool attribution trailers: no `Co-Authored-By` for an
assistant, no "generated with" lines, no emoji signatures. Write the message as
you would have written it yourself. Using an assistant to write the code is
fine; the commit log is for explaining the change, not the process.

## Pull requests

Small and focused beats large and complete. If a change does two things, two
pull requests are easier to review and easier to revert.

Say what you verified and how. "Ran the filesystem quickstart, opened a book,
switched profiles" is worth more than a green checkmark, given there are no
tests yet.

`main` takes changes through pull requests only, and all three CI jobs have to
pass before one can merge. Merges are squashed, so the branch can have as many
commits as it needs — write the final message on the pull request.

## Reporting a security issue

Please don't open a public issue for anything exploitable — see
[SECURITY.md](SECURITY.md), which explains where to send it and what does not
count (the missing authentication, chiefly).
